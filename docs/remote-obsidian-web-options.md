# Remote Obsidian browser access on KiroCrew

**Research snapshot:** 2026-09-09
**Scope:** Browser-based access to and editing of the existing decrypted checkout at `/var/lib/vault` on the headless `aarch64-linux` KiroCrew EC2 host. Primary sources are used throughout; repository activity and release versions are a point-in-time maintenance signal, not a guarantee.

## Executive recommendation

**Recommended: run the official ARM64 Obsidian desktop in one persistent Xpra session and expose Xpra's built-in HTML5 client only on `127.0.0.1`, reached through the existing SSM/SSH tunnel.** Xpra is designed to keep individual X11 applications alive across disconnects and includes a browser client, so the browser renders the real Obsidian process rather than a reimplementation ([Xpra README](https://github.com/Xpra-org/xpra/blob/master/README.md), [Xpra HTML5 client](https://github.com/Xpra-org/xpra-html5/blob/master/README.md)). Obsidian publishes an official Linux AArch64/ARM64 AppImage, and both Obsidian and Xpra are packaged in Nixpkgs for declarative deployment ([Obsidian downloads](https://obsidian.md/download), [Nixpkgs Obsidian expression](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/ob/obsidian/package.nix), [Nixpkgs Xpra expression](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/xp/xpra/package.nix)). This is the only evaluated option that simultaneously preserves Obsidian's core UI and plugin runtime, edits the existing checkout directly, adds no second synchronization engine, fits ARM64 NixOS, and follows the host's established loopback-plus-tunnel boundary.

**Fallback: code-server, restricted to `/var/lib/vault`, for reliable browser Markdown editing.** It ships ARM64 releases, defaults to loopback plus password authentication, and is substantially simpler than a remote GUI ([code-server install](https://coder.com/docs/code-server/install), [secure access guide](https://coder.com/docs/code-server/guide), [current release](https://github.com/coder/code-server/releases/tag/v4.136.2)). It is not Obsidian: it cannot provide Obsidian's graph, Bases, Live Preview behavior, core plugins, or community-plugin runtime. It is the right fallback when text editing and recovery matter more than fidelity.

Do **not** add Obsidian Sync, Obsidian Headless Sync, Self-hosted LiveSync, CouchDB, Syncthing, or another file synchronizer to this checkout. The current Git/git-crypt timer must remain the only remote synchronization path. Both Obsidian and LiveSync documentation warn against mixing synchronization systems on one vault, and Headless Sync warns against two Sync implementations on one device ([Obsidian sync guidance](https://github.com/obsidianmd/obsidian-help/blob/master/en/Getting%20started/Sync%20your%20notes%20across%20devices.md), [Headless Sync](https://github.com/obsidianmd/obsidian-help/blob/master/en/Obsidian%20Sync/Headless%20Sync.md), [LiveSync quick setup](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/quick_setup.md)).

## Current architecture and decision constraints

The deployed model is already a good base for browser access:

- `/var/lib/vault` is one unlocked, plaintext working tree backed by a private GitLab repository whose committed content is encrypted with git-crypt. KiroCrew owns the checkout, while Pasta receives read-only access ([ADR-002](adr/002-kirocrew-vault-git-crypt.md), [vault module, lines 19-107](../nixos/kirocrew-vault-git.nix#L19-L107)). Git-crypt protects the Git object store and remote, **not** the live decrypted filesystem; any browser service with vault access is therefore a high-value plaintext boundary ([ADR-002 encryption scope](adr/002-kirocrew-vault-git-crypt.md#encryption-scope)).
- KiroCrew writes note content directly. Its systemd namespace makes `.git`, `.obsidian`, and local indexes read-only to agents, while Pasta indexes the checkout read-only ([gateway paths, lines 249-270](../nixos/kirocrew-services.nix#L249-L270), [Pasta service, lines 291-344](../nixos/kirocrew-services.nix#L291-L344)).
- `kirocrew-vault-push` stages all changes, commits, fetches, rebases, and pushes. Its persistent timer starts after five minutes and then runs every ten minutes with up to 30 seconds of jitter ([push implementation, lines 110-147](../nixos/kirocrew-vault-git.nix#L110-L147), [timer, lines 200-218](../nixos/kirocrew-vault-git.nix#L200-L218)).
- Existing browser and dashboard services bind loopback: KiroCrew uses `KIROCREW_BIND=127.0.0.1`, and ttyd binds `127.0.0.1:7681`. Access is through AWS Systems Manager/SSH forwarding with no required inbound security-group port ([gateway environment, lines 272-287](../nixos/kirocrew-services.nix#L272-L287), [EC2 tunnel and ttyd configuration, lines 32-110](../nixos/kirocrew-ec2.nix#L32-L110)).
- The live flake output is `aarch64-linux`/Graviton ([flake output, lines 246-279](../flake.nix#L246-L279)). AWS specifies `t4g.xlarge` as 4 vCPU and 16 GiB RAM; it is burstable rather than sustained-compute hardware ([AWS T4g specification](https://aws.amazon.com/ec2/instance-types/t4/)).

There are two existing concurrency defects worth correcting during a later implementation, regardless of browser front end. First, the Git transaction has no shared lock. Second, after a successful local commit followed by a failed rebase or push, the next timer exits immediately when the working tree is clean and therefore does not retry an ahead-but-clean branch ([push implementation, lines 125-145](../nixos/kirocrew-vault-git.nix#L125-L145)). Browser access should not expand scope silently, but rollout should include a separate fix: serialize Git operations and always fetch/rebase/push when local `HEAD` is ahead, even with a clean worktree.

## What Obsidian officially offers in September 2026

The distinction between **editing**, **controlling a desktop app**, and **synchronizing files** is critical:

- **Official web app/browser editor: no documented product.** Obsidian's supported install catalog lists iOS, Android, Windows, macOS, Linux, and the Web Clipper, but no hosted browser editor ([official download page](https://obsidian.md/download), [official installation guide](https://github.com/obsidianmd/obsidian-help/blob/master/en/Getting%20started/Download%20and%20install%20Obsidian.md)). The Web Clipper captures browser content into a vault; it is not a vault editor ([Web Clipper](https://obsidian.md/clipper)).
- **Official server mode: none documented.** The desktop app remains a local application over a local folder. Obsidian explicitly describes a vault as Markdown files on the local filesystem and supports external editors by noticing filesystem changes ([data storage](https://github.com/obsidianmd/obsidian-help/blob/master/en/Files%20and%20folders/How%20Obsidian%20stores%20data.md)). Streaming that application is therefore remote display, not an Obsidian server API.
- **Official Obsidian CLI: yes, but not headless.** Public desktop 1.12 introduced the CLI; current documentation says the Obsidian app must be running and the first command starts it if necessary. The CLI controls commands and plugins inside that running app ([CLI documentation](https://github.com/obsidianmd/obsidian-help/blob/master/en/Extending%20Obsidian/Obsidian%20CLI.md), [1.12 announcement](https://obsidian.md/changelog/2026-02-27-desktop-v1.12.4/), [1.12.7 installer change](https://obsidian.md/changelog/2026-03-23-desktop-v1.12.7/)). It can complement the streamed process for automation; it does not create a browser UI.
- **Official headless client: yes, open beta, but Sync/Publish only.** `obsidian-headless` is a Node.js 22+ standalone client for Obsidian Sync and Publish. It supports one-shot or continuous Sync, but has no editor, plugin host, graph, or desktop UI ([official Headless overview](https://github.com/obsidianmd/obsidian-help/blob/master/en/Extending%20Obsidian/Obsidian%20Headless.md), [official repository](https://github.com/obsidianmd/obsidian-headless), [Headless Sync](https://github.com/obsidianmd/obsidian-help/blob/master/en/Obsidian%20Sync/Headless%20Sync.md)).
- **Official Obsidian Sync: synchronization, not browser editing.** It connects local vault copies to an off-site remote vault. End-to-end encryption is the default and protects the remote copy, but not local vaults ([Sync overview](https://github.com/obsidianmd/obsidian-help/blob/master/en/Obsidian%20Sync/Introduction%20to%20Obsidian%20Sync.md), [local and remote vaults](https://github.com/obsidianmd/obsidian-help/blob/master/en/Obsidian%20Sync/Local%20and%20remote%20vaults.md), [security and privacy](https://github.com/obsidianmd/obsidian-help/blob/master/en/Obsidian%20Sync/Security%20and%20privacy.md)). It would add a second synchronization authority without solving browser editing.

### Streaming implementation choices

**Xpra is the best fit.** Its scope matches the need: run one graphical application remotely, preserve it across disconnects, and serve a built-in HTML5 client ([Xpra README](https://github.com/Xpra-org/xpra/blob/master/README.md), [HTML5 README](https://github.com/Xpra-org/xpra-html5/blob/master/README.md)). Xpra provides socket-specific authentication modules and warns that password authentication over raw TCP needs encryption; use an encrypted listener plus a sops-provisioned secret even though the service is loopback-only ([Xpra authentication](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Authentication.md)). It also lets the deployment disable file transfer/open-file behavior and restrict clipboard direction ([file transfer controls](https://github.com/Xpra-org/xpra/blob/master/docs/Features/File-Transfers.md), [clipboard controls](https://github.com/Xpra-org/xpra/blob/master/docs/Features/Clipboard.md)). Its current Nixpkgs package removes the custom packaging burden.

**KasmVNC is technically strong but operationally second.** It is web-native, supports headless Linux, HTTPS Basic Authentication, WebRTC/WebGL/WebP, clipboard controls, and ARM64 packages ([overview](https://kasmweb.com/kasmvnc/docs/latest/index.html), [client](https://kasmweb.com/kasmvnc/docs/latest/clientside.html), [installation matrix](https://kasmweb.com/kasmvnc/docs/latest/install.html)). It can bind a specific interface and require SSL ([configuration](https://kasmweb.com/kasmvnc/docs/latest/configuration.html)). However, upstream's installation matrix does not include NixOS, and there is no `kasmvnc` package in current Nixpkgs. A custom derivation or container would become locally owned infrastructure. KasmVNC's documented minimum of 2 cores/2 GiB fits this host, but the 4-vCPU T4g has a 40% baseline per vCPU, so sustained desktop encoding should still be monitored rather than assumed free ([KasmVNC requirements](https://kasmweb.com/kasmvnc/docs/latest/install.html), [AWS T4g specification](https://aws.amazon.com/ec2/instance-types/t4/)).

**noVNC is a client, not the whole service.** Its own quick start requires an existing VNC server and either native WebSockets or `websockify`; it recommends loopback binding when public exposure is unnecessary ([noVNC README](https://github.com/novnc/noVNC/blob/master/README.md)). On NixOS this means owning and hardening an X server, VNC server, WebSocket proxy, static client, authentication, and TLS separately. That is more failure surface than Xpra's integrated server/client for no fidelity gain.

**`obsidian-remote` should not be adopted as-is.** The project explicitly warns against exposing port 8080 without securing it and documents default credentials/no-auth behavior depending on environment variables ([README](https://github.com/sytone/obsidian-remote/blob/main/README.md)). ARM64 support exists, but the current Dockerfile pins Obsidian 1.8.10 while official desktop has reached 1.13.8 ([Dockerfile](https://github.com/sytone/obsidian-remote/blob/f9b3206349ffe553776658251e1a0cef459d3efc/Dockerfile), [Obsidian 1.13.8](https://github.com/obsidianmd/obsidian-releases/releases/tag/v1.13.8)). Its last main-branch code commit was 2025-10-31 ([commit](https://github.com/sytone/obsidian-remote/commit/f9b3206349ffe553776658251e1a0cef459d3efc)). Recreating its useful shape from pinned official Obsidian plus current Xpra is simpler to audit and update than inheriting a Debian/LinuxServer/KasmVNC container stack.

### Non-streaming choices

**The existing KiroCrew dashboard/CLI remains valuable for intent-level work.** It already gives agents write access to the same checkout, while ttyd provides a browser terminal. It is good for “summarize this meeting and update the project” or scripted file edits. It is not direct note navigation, Live Preview, graph/Bases interaction, drag-and-drop attachments, or visual plugin use, so it cannot replace an Obsidian UI.

**code-server is the strongest non-Obsidian editor.** Obsidian intentionally stores Markdown as ordinary files and reloads external changes, making a filesystem editor safe at the format level ([Obsidian data storage](https://github.com/obsidianmd/obsidian-help/blob/master/en/Files%20and%20folders/How%20Obsidian%20stores%20data.md)). code-server provides VS Code in the browser, official ARM64 artifacts, and a current Nixpkgs expression ([project](https://github.com/coder/code-server), [install/ARM64](https://coder.com/docs/code-server/install), [Nixpkgs expression](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/co/code-server/package.nix)). Its default is `127.0.0.1:8080` plus a random password, and its maintainers warn that exposure without authentication and encryption permits machine takeover through the terminal ([FAQ](https://coder.com/docs/code-server/FAQ), [secure access guide](https://coder.com/docs/code-server/guide)). For this use, disable the integrated terminal, port proxy, file downloads, and extension installation unless explicitly needed. The decisive limitation is fidelity: VS Code/Open VSX extensions are not Obsidian plugins, and code-server itself documents marketplace/runtime differences from desktop VS Code ([code-server FAQ](https://coder.com/docs/code-server/FAQ)).

**LiveSync/CouchDB is not browser editing.** Self-hosted LiveSync is a community Obsidian synchronization plugin backed by CouchDB/object storage/WebRTC. It explicitly says it is incompatible with official Sync and must not run beside another synchronization solution ([LiveSync README](https://github.com/vrtmrz/obsidian-livesync)). Its setup guide requires disabling every other writer/synchronizer and protecting database/setup credentials ([quick setup](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/quick_setup.md)). CouchDB can bind only `127.0.0.1` and requires an administrator account, but it still adds a second database, credential set, backup/compaction lifecycle, and replication conflict model ([CouchDB single-node setup](https://docs.couchdb.org/en/stable/setup/single-node.html)). It solves device replication, not browser rendering, and conflicts directly with the “one Git sync authority” constraint.

**Official Sync/Headless is also not browser editing.** Headless can watch and continuously sync a local directory, and its own documentation warns not to run desktop Sync and Headless Sync on the same device ([Headless Sync](https://github.com/obsidianmd/obsidian-help/blob/master/en/Obsidian%20Sync/Headless%20Sync.md)). Adding it to `/var/lib/vault` would make Obsidian's remote vault and GitLab/git-crypt concurrent authorities. It is appropriate only after a deliberate migration away from Git synchronization, not as browser access layered onto this design.

## Proposed architecture

```text
Browser on operator device
  │
  │ existing SSM/SSH local port forward
  ▼
127.0.0.1:<dedicated-port> on EC2
  │
  ▼
Xpra HTML5 endpoint (TLS + authentication, one session)
  │
  ▼
official Obsidian ARM64 process in Xpra's virtual X display
  │
  ├── read/write: /var/lib/vault notes, attachments, .obsidian
  ├── no access:  /var/lib/vault/.git, secrets, KiroCrew home/code
  └── private app state: /var/lib/obsidian-web
          │
          ▼
/var/lib/vault  ◄──────── KiroCrew agent writes
  │
  ├── Pasta reads only
  └── existing 10-minute Git/git-crypt service remains sole sync engine
          │
          ▼
      encrypted GitLab remote
```

Use one persistent Obsidian process, not one process per browser tab. Browser reconnects should attach to that session. Obsidian watches external filesystem changes, so KiroCrew edits appear without replication ([Obsidian data storage](https://github.com/obsidianmd/obsidian-help/blob/master/en/Files%20and%20folders/How%20Obsidian%20stores%20data.md)). There is still application-level same-file concurrency: an agent and operator can edit the same note at once. No display protocol fixes that. Operationally, avoid assigning an agent work on a note currently open for manual editing, and rely on Git history plus explicit conflict review for mistakes.

### Service identity and filesystem boundary

Prefer a dedicated `obsidian-web` system user rather than running the GUI as `kirocrew`. Give it ACL-based write access to vault content and `.obsidian`, then make `.git` inaccessible inside the service namespace. This preserves KiroCrew's process boundary while allowing Obsidian to persist its vault-local settings. Obsidian documents that `.obsidian` contains preferences, themes, hotkeys, and community plugins ([configuration-folder documentation](https://github.com/obsidianmd/obsidian-help/blob/master/en/Files%20and%20folders/How%20Obsidian%20stores%20data.md)). Keep `.obsidian` excluded from Git as ADR-002 already specifies, unless a separate decision changes that policy ([ADR-002](adr/002-kirocrew-vault-git-crypt.md#encryption-scope)).

Give the service its own `HOME`, XDG config/cache/data directories, and `StateDirectory`. Do not grant access to `/var/lib/kirocrew/secrets`, `/home/orre`, the 1Password relay, Git credentials, or the Git object/index. Make `.gitattributes` and `.gitignore` read-only so the browser process cannot weaken git-crypt coverage or exclusion rules.

## Security controls

1. **Network:** bind only IPv4 loopback; add no firewall/security-group ingress; reach it only through the existing SSM/SSH tunnel. Disable Xpra mDNS/session advertisement and any listener other than loopback. This mirrors the current dashboard and ttyd design ([EC2 module](../nixos/kirocrew-ec2.nix#L32-L110)).
2. **Transport and authentication:** use Xpra TLS plus a strong sops-provisioned authentication secret. Xpra explicitly warns that password authentication on unencrypted TCP is vulnerable to interception and documents file, SCRAM, PAM, OAuth, FIDO2, and rate-limit modules ([authentication](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Authentication.md)). Tunnel access is necessary but should not be the only browser-session control.
3. **Least privilege:** dedicated UID; `ProtectSystem=strict`; `ProtectHome=true`; private `/tmp`; IMDS deny for `169.254.169.254`; no supplementary secrets groups; service write access limited to vault content, `.obsidian`, and its state. Make `.git`, credentials, and unrelated checkouts inaccessible.
4. **Remote-desktop feature reduction:** disable Xpra file transfer, remote file opening, printing, webcam, microphone, speaker, command launching, and session sharing. File transfer is enabled by default upstream and `open-files` carries an explicit security warning ([Xpra file transfers](https://github.com/Xpra-org/xpra/blob/master/docs/Features/File-Transfers.md)). Enable clipboard only if required; prefer client-to-server only and a size/filter limit because Xpra supports directional and regex controls ([Xpra clipboard](https://github.com/Xpra-org/xpra/blob/master/docs/Features/Clipboard.md)).
5. **Obsidian/plugin policy:** start in Restricted Mode, inventory required community plugins, and enable only pinned/trusted plugins. Plugins execute inside the process that can read the plaintext vault; full fidelity necessarily gives them that authority. Keep plugin auto-update a deliberate maintenance decision rather than an uncontrolled deployment path.
6. **Git integrity:** browser service cannot invoke Git or alter `.git`, `.gitattributes`, or `.gitignore`. The existing systemd Git service remains the sole process authorized for repository metadata and remote credentials. Add a lock around Git operations and correct ahead-but-clean retry behavior before broad use.
7. **Data handling:** do not log note contents, keystrokes, clipboard payloads, URLs containing file names, or screenshots. Keep Xpra/Obsidian caches under protected local state; include only necessary state in backups. Remember that filenames and paths are intentionally not protected by git-crypt on the remote ([ADR-002](adr/002-kirocrew-vault-git-crypt.md#encryption-scope)).
8. **Session lifecycle:** one exclusive interactive session, idle disconnect, and a documented stop command that terminates Obsidian cleanly. A disconnected browser may leave the app running for fast reattachment, but an operator must be able to stop it before maintenance or incident response.
9. **Resource controls:** set systemd memory/CPU ceilings and observe CPU credits, resident memory, and encoder load during scroll-heavy use. KasmVNC's 2-core/2-GiB minimum and code-server's 2-core/1-GiB recommendation show that the host has nominal capacity, but T4g sustained CPU is credit-governed ([KasmVNC requirements](https://kasmweb.com/kasmvnc/docs/latest/install.html), [code-server requirements](https://github.com/coder/code-server/blob/main/docs/requirements.md), [AWS T4g](https://aws.amazon.com/ec2/instance-types/t4/)).

## Rollout outline

1. **Preflight and backup.** Confirm the vault timer is healthy, local `HEAD` equals upstream, no rebase is in progress, and a current encrypted remote plus separate recovery copy exist. Record the current Obsidian/plugin versions on the workstation.
2. **Package declaratively.** Pin current Nixpkgs Obsidian and Xpra inputs for `aarch64-linux`; do not curl mutable binaries at service start. Validate licenses and hashes through the flake. Use Xpra's bundled HTML5 client rather than adding a separate noVNC/websockify path.
3. **Create the isolated service.** Add the dedicated user/state, narrow vault ACL, systemd hardening, loopback-only encrypted listener, authentication secret, exclusive session, disabled transfer/peripheral features, and explicit `.git`/secret denial. Keep the service opt-in at first.
4. **Correct Git transaction handling.** In a separate reviewed change, serialize clone/push Git operations and make the timer push an ahead-but-clean branch. Do not add any Sync plugin or daemon.
5. **First-run initialization.** Open `/var/lib/vault` as the only vault. Keep `.obsidian` local. Start in Restricted Mode, then enable required plugins one at a time. Verify the app uses its private global config/state path rather than an operator or KiroCrew home.
6. **Functional test through the tunnel.** Test create/edit/delete, wikilinks, rename-with-link-update, attachments, search, graph/Bases used in practice, clipboard policy, browser reconnect, Obsidian restart, and host reboot. Confirm no listener exists on a non-loopback address.
7. **Concurrency and persistence test.** While Obsidian is open, make a KiroCrew edit to a different note and verify Obsidian notices it. Then test a controlled same-note collision, inspect the result, run the timer, and verify the GitLab blob remains ciphertext. Simulate push failure after commit and verify the corrected timer retries the clean-but-ahead branch.
8. **Observe before defaulting on.** Track Xpra/Obsidian crashes, CPU credits, RSS, input latency, tunnel disconnect behavior, timer duration/failures, and Git divergence for at least several normal work sessions.
9. **Rollback.** Stop/disable the Xpra unit, remove the dedicated ACL and state after preserving any desired `.obsidian` settings, and leave `/var/lib/vault` plus the existing Git timer untouched. The code-server fallback can be enabled against the same checkout without a data migration.

## Why the rejected options are inferior

- **KiroCrew dashboard/CLI alone:** already secure and useful, but indirect. It cannot provide the visual Obsidian workflow requested.
- **KasmVNC:** good browser remote-desktop technology and healthy ARM64 upstream, but its supported binary matrix omits NixOS. Owning a custom package/container and a full desktop stack is unnecessary when Xpra already packages the single-app use case in Nixpkgs.
- **noVNC:** actively maintained and portable, but it is only the browser client. Adding the VNC server and WebSocket proxy increases components and security configuration without improving Obsidian fidelity.
- **`obsidian-remote`:** convenient proof that the model works, but the image is behind current Obsidian and brings a mutable community container/base-image supply chain plus unsafe-if-unset authentication defaults. It is less reproducible than a pinned Nix service.
- **code-server as primary:** operationally excellent, but it is a Markdown/code editor, not Obsidian. Use it for recovery and low-bandwidth editing, not as the main experience.
- **LiveSync/CouchDB:** solves synchronization between Obsidian clients, not browser editing. Its own documentation requires other sync systems to be disabled, directly opposing the retained Git/git-crypt authority.
- **Official Obsidian Sync/Headless:** current and security-conscious, but still synchronization rather than editing. Headless is open beta and adding it would create the same dual-authority problem as LiveSync.
- **Official Obsidian CLI:** valuable automation for the recommended running desktop process, but it explicitly depends on that process and supplies no browser UI by itself.

## Decision

Adopt **official Obsidian ARM64 + Xpra HTML5 over the existing tunnel**, operating directly on `/var/lib/vault`, with Git/git-crypt remaining the sole synchronization engine. Keep **code-server** as the one fallback for lightweight or recovery editing. Treat KasmVNC as a transport contingency only if Xpra fails an actual ARM64/Electron smoke test; do not deploy `obsidian-remote`, LiveSync/CouchDB, or official Sync/Headless alongside the existing Git timer.
